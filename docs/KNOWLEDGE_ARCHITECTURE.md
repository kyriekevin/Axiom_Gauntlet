# Knowledge Note Architecture Proposal

[English](KNOWLEDGE_ARCHITECTURE.md) | [简体中文](KNOWLEDGE_ARCHITECTURE_zh-CN.md)

> Status: adopted foundation. Actual topic content is added separately through notes branches.

## Problem

The current structure puts three different concerns in every problem README:

- problem facts: source, state, accepted languages, and implementations;
- reusable knowledge: modeling, recursion, memoization, DP, proofs, and optimizations;
- learning evidence: initial solves, documentation passes, and later reviews.

When 486 and 877 share the same interval-game model, full per-problem notes repeat the same derivation. A single concept-level review is also misrepresented as separate documentation work on every included problem.

## Target model

Separate problem records from reusable knowledge:

```text
problems/<platform>/<id>/
├── problem.toml
├── solution.py
└── README.md / README_zh-CN.md   # lightweight problem card or generated entry point

knowledge/
├── INDEX.md / INDEX_zh-CN.md     # generated knowledge catalog
├── LOG.md                        # append-only maintenance history
└── dynamic-programming/
    ├── README.md / README_zh-CN.md
    ├── memoization/
    └── interval-dp/
        ├── topic.toml            # identity, examples, dependencies, and activity
        ├── README.md
        ├── README_zh-CN.md
        └── assets/               # visuals that serve the shared concept
```

### Problem layer

The problem layer preserves facts that cannot be replaced by a topic note:

- platform identity, difficulty, and tags;
- platform-confirmed AC events;
- exact accepted implementations;
- time and space complexity for each implementation;
- boundaries or differences unique to that problem.

Problem READMEs stop acting as complete tutorials. They may remain as lightweight GitHub-facing cards, with related knowledge links generated by scanning the knowledge layer.

### Knowledge layer

The knowledge layer combines a stable taxonomy with cross-linked pages instead of starting with many flat topics. An OI Wiki-style subject tree keeps major areas such as dynamic programming, graph theory, and data structures systematic. LLM Wiki-style indexes, backlinks, and maintenance logs keep related ideas connected across that tree.

The canonical home for 486 and 877 should be `dynamic-programming/interval-dp`, not a top-level `interval-game-dp` topic. The interval DP page can distinguish two common transition families:

- split and merge: enumerate a split point `k` and combine two subintervals;
- interval shrinking: choose an endpoint and transition to `[i + 1, j]` or `[i, j - 1]`.

These two problems are zero-sum game examples of the second family. That section would proceed through:

1. modeling endpoint choices under optimal play as a zero-sum game;
2. defining the recursive state and choices;
3. implementing memoized search;
4. deriving bottom-up interval DP from dependency order;
5. compressing space;
6. checking whether parity or another mathematical property collapses the general DP.

Problems become examples with explicit roles: 486 demonstrates the general model and tie condition, while 877 demonstrates the same model plus a constraint-specific shortcut. Memoization is reusable across many DP families and therefore deserves its own page; the interval DP page links to it and shows only its application to the current state graph.

### Sources, wiki, and schema

Karpathy's LLM Wiki pattern maps naturally onto this repository:

- sources: platform facts, accepted code, and activity under `problems/`, plus explicitly cited external material;
- wiki: continuously synthesized and cross-linked pages under `knowledge/`;
- schema: repository docs, validators, and the review skill that define page granularity, maintenance workflows, and quality gates.

`INDEX` is the content-oriented entry point, while `LOG` is the append-only chronological maintenance record. Periodic lint should detect orphan pages, dead links, near-duplicate topics, and missing backlinks rather than checking Markdown shape alone.

## Single source of truth

A topic can use a small `topic.toml`:

```toml
version = 1
path = "dynamic-programming/interval-dp"
title = "Interval DP"
title_zh_cn = "区间动态规划"
tags = ["dynamic-programming", "interval"]
links = ["dynamic-programming/memoization", "mathematics/game-theory"]

[[examples]]
uid = "leetcode:0486"
role = "endpoint-game-general-model"

[[examples]]
uid = "leetcode:0877"
role = "constraint-shortcut"

[[activity]]
type = "review"
date = 2026-08-02
result = "pass"
```

Example relationships live only in `topic.toml`, avoiding duplicate relationship maintenance. The generated knowledge index provides the current navigation entry point; richer reverse problem-to-topic links can be added later from the same data. Before creating a page, the maintainer checks `INDEX` and adjacent pages. A subsection becomes its own page only when it has an independent definition, is reused from multiple pages, or has its own review prompts and example set.

## Lifecycle and activity

The long-term direction separates two lifecycles:

- problems: `draft -> accepted`;
- knowledge topics: progress from a draft into a reviewable note and record their own `note` and `review` events.

One interval DP review is then counted once rather than once per example problem. The existing problem-level `documented` state remains temporarily for compatibility and is not removed in the first migration.

## Workflow and skill boundaries

- `axiom-practice` handles daily solving: scaffolding, spoiler-controlled help, AC confirmation, code review, complexity, and problem-specific deltas.
- A separate review skill handles periodic synthesis: abstracting a shared model from multiple problems, checking transfer, maintaining a knowledge topic, and creating useful visuals.
- `practice/YYYY-MM-DD` contains problem evidence; `notes/YYYY-MM-DD` updates one or more knowledge topics.

Visual assets belong to the canonical knowledge page rather than being copied into each problem. For endpoint games, the visual should show the derivation from modeling through recursion, memoization, interval DP, and finally a mathematical special case. Image generation should wait until the interval DP page structure is approved.

## Branch and delivery boundaries

- `codex/knowledge-notes-architecture` changes only the repository foundation: this architecture contract, problem-record simplification, the knowledge schema, validators/CLI/templates, and practice/review skill responsibilities. It does not write the final 486/877 knowledge content or record this review activity.
- After the architecture branch is merged, `notes/YYYY-MM-DD` creates or updates knowledge pages, adds examples, generates visuals, and records the real review.

This boundary keeps infrastructure PR review focused on contracts and deterministic tooling, while notes PR review focuses on whether the knowledge is accurate, systematic, and useful for recall.

## Adopted decisions

- Durable content lives under `knowledge/`; `notes/YYYY-MM-DD` names the short-lived review branch.
- Problem READMEs remain lightweight source cards.
- Accepted-solution complexity lives in `problem.toml`.
- `axiom-practice` and `axiom-review` have separate daily-practice and delayed-review roles.
- Knowledge activity has its own generated log and does not inflate the problem activity heatmap.
