# Axiom Coach 工作流

[English](COACH_WORKFLOW.md) | [简体中文](COACH_WORKFLOW_zh-CN.md)

Axiom Coach 是现有练题与复习流程之前的选题层。它负责消除“今天到底练什么”的空白页，
但不会把练习变成连续打卡、配额或从头重播固定课程。

## 只需记住三句话

默认入口是一句对 Codex 说的话，不是终端命令。日常练习从这句开始：

```text
今天练什么？
```

需要显式指定 Skill 时也可以说：

```text
$axiom-coach 今天练什么？
```

Coach 会查看仓库中的实际证据，只给一个主推荐，同时保留 `轻一点`、`换路线` 和
`今天不练` 三个出口。只有平台、时间或难度确实会改变本次安排时，才会追问。

也可以直接表达意图：

```text
今天想恢复差分。
今天练 AI，控制在 30 分钟左右。
继续上次的知识点。
今天轻一点。
```

这些只是你对默认推荐的覆盖，不需要先配置一套模式。

周度与月度入口同样简单：

```text
复盘这周。
做本月路线检查。
```

| 尺度 | 会发生什么 | 不会发生什么 |
|---|---|---|
| 每日 | 一个简短诊断，然后进入最小必要的学习、尝试或解题动作 | 必须一路走到 AC 的固定流水线 |
| 每周 | 证据足够时，用一道延迟、隐藏知识点的检查替代当天主练习；知识沉淀按需进行 | 额外作业、周配额，或练得少时补欠账 |
| 每月 | 用 5–10 分钟决定接下来继续、降难、暂停或探索什么 | 覆盖率报表、课程进度审计或 backlog |

每日、每周、每月是三种观察尺度，不是三份叠加作业。它们只在有价值时触发，跳过不会
产生学习债务。

## 主动、教练主导与定时提醒

| 交互 | 谁选择知识点 | 如何启动 |
|---|---|---|
| 教练主导的拉取 | Coach | 你说“今天练什么？” |
| 主动指定 | 你 | 指定路线、知识点、时间或调整方向 |
| 定时提醒 | Coach automation | 另行创建的定时任务 |

仓库 Skill 自己不能主动发起对话。真正的每日推送需要单独配置 automation，应该等人工流程
走顺后再决定，而且始终可选，不制造逾期任务或 streak。

## 职责怎么流转

```text
Axiom Coach
  选知识点 → 闭卷诊断 → 校准下一步
        │
        ├── 已选定具体 OJ 题 → Axiom Practice
        │      建骨架 → 独立解题 → 平台确认 AC → 当日 PR
        │
        └── 值得延迟重建的通用知识 → Axiom Review
               整理主题 → 记录复习证据 → notes PR
```

你负责接受、覆盖或拒绝推荐，再独立解题、提交并确认 Accepted。仓库检查、建骨架、Git、
生成产物、验证、Skill 路由和 PR bookkeeping 由 agent 处理。

## 学习怎么推进

阶段按诊断裁剪，不是固定流水线：

```text
Recall / 闭卷诊断
├── 概念基本空白 ─────────────→ Learn
├── 理解但实现生疏 ───────────→ Anchor
├── 模板会但识别困难 ─────────→ Guided transfer
└── 已有近期迁移证据 ─────────→ Delayed blind check
```

同一次 session 的变形题不称为盲测。真正的 blind check 放到后续 session，或至少隔开一道
无关题；在尝试结束或你主动求助前，不展示 topic、tag 或带有解法暗示的选题理由。
题名本身会暴露目标技巧的题也不会被选作盲测。

算法与 AI 共用这套交互，但不共用一套虚假的能力判定。AI 知识点可能分别需要概念、实现
和实验三类证据；一个小函数 AC 只覆盖其中一部分。

对于难度合适的 OJ，真正有价值的过程不只是“写代码然后 AC”：

```text
理解与建模 → 不变量与复杂度 → 独立实现
→ 反例或压力测试 → 调试 → 平台确认 AC → 代码 review
```

这是一条可能的完整闭环，不是每天必须填完的表。一次 session 可以停在有效学习、认真尝试
或定位到真实卡点；测试、调试和 review 只有真的发生过，才算训练到了。

## 证据分别说明什么

| 层次 | 例子 | 能说明什么 |
|---|---|---|
| 结果证据 | 平台 Accepted，加上时间与空间复杂度 | 一次具体提交的结果 |
| 过程证据 | 建模、提示程度、反例、bug、测试策略或代码 review | 本次 session 实际练到了什么 |
| 能力证据 | 延迟、隐藏知识点、陌生且尽量独立的解题或知识重建 | 对提取与迁移能力更强的一次观察 |

AC 很有价值，但它不是“已经掌握”的标签。没有观察到的过程保持 unknown，一次延迟成功也
仍然只是一次有日期的观察。周/月只使用“已有证据 / 尚无证据 / 需要再观察”，不转换成
百分比或分数。

## 主要能力提升点

| 能力 | 如何训练 | 边界 |
|---|---|---|
| 提取与识别 | 闭卷诊断和延迟隐藏知识点检查 | 刚看完模板的复现不算延迟证据 |
| 拆解与建模 | 把题意转成状态、图结构或子问题 | AC 本身看不出使用了什么模型 |
| 正确性与复杂度 | 不变量、边界、反例与代价分析 | OJ 测试不是正确性证明 |
| 实现、测试与调试 | 独立编码、手造样例、压力测试和故障定位 | 只有实际做过才会提升 |
| AI 生成算法代码 review | 检查模型、不变量、边界、复杂度与反例 | 不等同于完整的架构、安全、可维护性或系统工程 review |
| AI 基础 | 分开观察概念、实现和实验 | Deep-ML 小函数 AC 通常只覆盖实现 |

## 当前 pilot 的边界

当前版本定义的是人机协作工作流与 Skill handoff，并不声称 Axiom 已经拥有完整 curriculum
或稳定的确定性推荐器。最初几次 session 的诊断与提示级别只保留在对话里，不改动现有
`problem.toml` 和 `topic.toml` 契约。是否值得让 curriculum、CLI 或 schema 长期记录推荐角色、
信息披露、提示和 checkpoint 结果，要由真实 session 中反复出现的需要决定，而不是先设计
一个想象中的 mastery 模型。
